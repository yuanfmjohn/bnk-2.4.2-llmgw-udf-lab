## Pre-Flight Lab Health Checks

Before applying AI Gateway resources on a freshly booted or restored UDF lab, verify these prerequisites on `controller`:

1. **Cluster License & BNK Pods**:
   ```bash
   kubectl get license -A
   kubectl get cneinstance f5-bnk-instance -n f5-bnk-instance
   kubectl get pods -n f5-cne-core
   kubectl get pods -n f5-bnk-instance -o wide
   ```
   Confirm `f5-cne-cluster-license` is `Active`, all `f5-tmm-*` pods are `7/7 Running`, `f5-cne-controller` is `3/3 Running`, and all `f5-dssm-db-[0..2]` pods are `3/3 Running`.

   > **Note (DSSM TLS Rotation Check):** If `f5-dssm-db-*` pods are `2/3 Running` with `SSL_connect failed: certificate verify failed` (which causes `/api/v1/tenants` on `f5-cne-controller-api:8443` to return `HTTP 500`), delete the unready `f5-dssm-db-*` pods so `redis-server` restarts with the rotated TLS certificate from `/tls/dssm/mds/svr/tls.crt`:
   > ```bash
   > kubectl delete pod f5-dssm-db-0 f5-dssm-db-2 -n f5-bnk-instance
   > kubectl wait --for=condition=Ready pod -l app=f5-dssm-db -n f5-bnk-instance --timeout=120s
   > ```

2. **Host Secondary NICs & TMM Data-Plane Connectivity**:
   Multus `macvlan` (`passthru`) interfaces (`external-vlan` on `ens6`, `internal-vlan` on `ens7`, `cnf` on `ens8`) require the parent physical interfaces on `worker1` and `worker3` to be administratively `UP`. Ensure `/etc/netplan/99-extra-nics.yaml` on `worker1` and `worker3` is valid YAML and all three interfaces are up:
   ```bash
   sudo ip link set ens6 up && sudo ip link set ens7 up && sudo ip link set ens8 up
   ```
   Verify TMM data-plane reachability to the external gateway (`10.1.200.1`) and internal VLAN peer (`10.1.210.70`):
   ```bash
   kubectl exec daemonset/f5-tmm -n f5-bnk-instance -c debug -- ping -c 2 10.1.200.1
   kubectl exec daemonset/f5-tmm -n f5-bnk-instance -c debug -- ping -c 2 10.1.210.70
   ```

## Deployment Steps (Primary: Google Gemini)

### 1. Apply Infrastructure, Gemini Provider, and Gateway API Resources

Apply the GatewayClass, Tenant, Gemini provider chain (`gemini/02`–`06`), and Gateway/HTTPRoute/AppPolicy sequentially (set your Google AI Studio API key in `gemini/02-secret-pk-demo-gemini.yaml` first):

```bash
cd /home/ubuntu/aigateway

kubectl apply -f 00-bnk-gatewayclass.yaml
kubectl apply -f 01-ai-tenant-demo.yaml
kubectl apply -f gemini/02-secret-pk-demo-gemini.yaml
kubectl apply -f gemini/03-ai-credential-gemini.yaml
kubectl apply -f gemini/04-ai-provider-gemini.yaml
kubectl apply -f gemini/05-ai-model-gemini.yaml
kubectl apply -f gemini/06-ai-gateway-profile-gemini.yaml
kubectl apply -f 07-gateway.yaml
kubectl apply -f 08-httproute.yaml
kubectl apply -f 09-apppolicy.yaml
```

> **Note (Convergence Timing):** `AIProvider` takes approximately 4–5 minutes to resolve the upstream FQDN and commit `f5-bnk-instance.pk-demo-gemini-aigw-pool` across all TMM endpoints (`Programmed: True`).

Verify resource status:
```bash
kubectl get aitenant demo
kubectl get aicredential,aiprovider,aimodel,aigatewayprofile,gateway,httproute,apppolicy -n f5-bnk-instance
```

> **Alternative Provider Option (NVIDIA NGC / OpenAI-Compatible):**
> To test an OpenAI-compatible provider instead of Google Gemini, set your NVIDIA NGC key (`nvapi-...`) in `02-secret-pk-demo-ngc.yaml` and apply `02-secret-pk-demo-ngc.yaml` through `06-ai-gateway-profile.yaml` in place of `gemini/02`–`06`.

### 2. Configure Governance & Virtual Keys

Run the automated key setup script on `controller`:

```bash
python3 /home/ubuntu/aigateway/governance/setup_keys.py
```

What `setup_keys.py` does:
1. Authenticates against `f5-cne-controller-api` (`http://<endpoint-ip>:8443/api/v1/auth/login`) using credentials from Secret `f5-aigateway-admin`.
2. Ensures the governance hierarchy exists in tenant `demo`: restores `demo-org` from `/api/v1/tenants/demo/governance-tombstones` if previously deleted (or creates it), locates/creates its default team, and creates/reactivates service principal `demo-app`.
3. Issues an active virtual key scoped to `gemini-flash-latest`, `gemini-3.5-flash-lite`, `deepseek-ai/deepseek-v4.1-flash`, and `openai/gpt-oss-20b`, saving the bearer token to `/home/ubuntu/aigateway/tests/demo_vkey.txt`.

### 3. Verify Traffic Through Data Plane (`client` Host)

Copy `/home/ubuntu/aigateway/tests/` (including `demo_vkey.txt`) to the `client` host (`10.1.10.4`, which routes to `10.1.200.0/24` via `10.1.10.1`) and run the test suite against VIP `10.1.200.85`:

```bash
/home/ubuntu/aigateway/tests/run_test.sh 10.1.200.85
```

This verifies:
- `GET /v1/models` -> `HTTP/1.1 200 OK`
- `POST /v1/chat/completions` (`gemini-flash-latest`) -> `HTTP/1.1 200 OK`
- Unauthorized model (`gpt-4o-mini`) -> `HTTP/1.1 403 Forbidden` (`model_not_allowed`)
- Invalid virtual key -> `HTTP/1.1 401 Unauthorized` (`token_not_found_in_db`)

### 4. Access the AI Gateway Console & Credentials

The `f5-aigateway-console` service is exposed via `NodePort` (`3000:30964/TCP`) and via the **`llmgw-console`** UDF access shortcut on **`worker4`** (`http://<node-ip>:30964`, e.g., `http://10.1.1.9:30964`).

Retrieve the System Admin (`f5-aigateway-admin`) and Tenant Admin (`aitenant-<tenant>-admin`) login credentials from namespace `f5-bnk-instance`:

```bash
# System Admin
kubectl get secret f5-aigateway-admin -n f5-bnk-instance -o jsonpath='{.data.username}' | base64 --decode; echo ""
kubectl get secret f5-aigateway-admin -n f5-bnk-instance -o jsonpath='{.data.password}' | base64 --decode; echo ""

# Tenant 'demo' Admin
kubectl get secret aitenant-demo-admin -n f5-bnk-instance -o jsonpath='{.data.username}' | base64 --decode; echo ""
kubectl get secret aitenant-demo-admin -n f5-bnk-instance -o jsonpath='{.data.password}' | base64 --decode; echo ""
```

### 5. Verify OpenTelemetry Telemetry in ClickHouse

On `controller`, inspect the recorded inference and audit records in `otel.aigw_requests`:

```bash
kubectl exec f5-aigateway-clickhouse-0 -n f5-bnk-instance -- clickhouse-client --query \
  "SELECT timestamp, request_id, principal_id, team_id, org_id, deployment_upstream, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, gen_ai.f5.usage.total_tokens, gen_ai.f5.latency_ms, gen_ai.f5.latency_gate_us, http.response.status_code, error.type FROM otel.aigw_requests ORDER BY ts_ms DESC LIMIT 5 FORMAT Vertical;"
```

## Fixes Applied During Lab Guide Validation

The following discrepancies in the original lab notes were identified and corrected:
1. **`worker1` / `worker3` Secondary NICs (`ens6`–`ens8`)**: Fixed malformed `/etc/netplan/99-extra-nics.yaml` (`ethernets:      ens6:` missing newline) and brought `ens6`, `ens7`, `ens8` `UP` so TMM `macvlan` (`passthru`) interfaces pass ARP/traffic.
2. **DSSM 1-Hour TLS Certificate Readiness**: Documented restarting unready `f5-dssm-db-*` pods when `redis-server` retains an expired in-memory cert (`HTTP 500` from `f5-cne-controller-api`).
3. **`gemini/05-ai-model-gemini.yaml`**: Replaced deprecated `gemini-2.5-flash` (`404` from Google AI Studio) with `gemini-3.5-flash-lite` and added required `pricing` (`inputPerMtok` / `outputPerMtok`).
4. **`gemini/06-ai-gateway-profile-gemini.yaml`**: Fixed CRD fields (`auth.virtualKeys: {}` and `providers: [{ providerRef: { name: pk-demo-gemini } }]`) and set `metadata.name: demo-llm` to match `09-apppolicy.yaml`.
5. **`governance/setup_keys.py`**: Fixed `NameError` on line 55 (`k.get(id)` -> `k.get('id')`, etc.) and added idempotent org/team/principal bootstrap including `/api/v1/tenants/demo/governance-tombstones/orgs/{id}/restore` support when re-running after cleanup.

## Clean Up / Wind Down Steps

To wind down the `demo` tenant:
1. Revoke Virtual Keys and delete/purge governance entities via the controller API (`/api/v1/tenants/demo/virtual-keys`, `/api/v1/tenants/demo/governance/orgs/...`, and `/api/v1/tenants/demo/governance-tombstones/orgs/...` if re-creating with the same ID).
2. Delete the Kubernetes resources in reverse order:
   ```bash
   kubectl delete -f 09-apppolicy.yaml
   kubectl delete -f 08-httproute.yaml
   kubectl delete -f 07-gateway.yaml
   kubectl delete -f gemini/06-ai-gateway-profile-gemini.yaml
   kubectl delete -f gemini/05-ai-model-gemini.yaml
   kubectl delete -f gemini/04-ai-provider-gemini.yaml
   kubectl delete -f gemini/03-ai-credential-gemini.yaml
   kubectl delete -f gemini/02-secret-pk-demo-gemini.yaml
   kubectl delete -f 01-ai-tenant-demo.yaml
   ```
